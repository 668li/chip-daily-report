# ADR · 护城河迭代冲刺（2026-09-26）

> 只记「自决且影响后续会话」的决策；一次性小决定进迭代台账循环备注。

## ADR-001 心跳方案：CronCreate 工作日 08:00 + daily_runner.py
- **背景**：F4 已死（WorkBuddy 不再运行），日报停摆中；护城河五论点均以每日心跳为前提。发射四问 Q1 无人应答，按推荐执行。
- **选项**：① 重建 WorkBuddy 类外部自动化（本环境无此能力）② Windows 计划任务 + 纯脚本全自动（内容生成无法纯脚本化）③ 本 harness CronCreate 定时唤起 LLM 会话 + runner 脚本做机械链路与验收器。
- **决定**：选项③。CronCreate 注册「周一至五 08:00」唤起会话，会话内先跑 `scripts/daily_runner.py`（discover quick → prepare_candidates → 校验 → HTML），再按 SKILL.md 六步流程生成当期日报。失败即响 = 定时会话运行结果用户直接可见 + runner 非零退出指明炸在哪步。心跳节奏沿用历史 F4 约定（工作日），台账「心跳连续天数」按工作日记。
- **删除方法**：对本 harness 说「删除芯片日报每日唤起的定时任务」或列出 automation 后按 id 删除（CronDelete），一步生效，无残留。
- **复审条件**：连续 3 次误报/漏报；或用户要求 7 天心跳 / 改时间。

## ADR-002 runner 与 LLM 分工
- **背景**：日报正文创作（选题/写作/教学层）是 LLM 工作，无法纯脚本化；但机械链路（发现/采集/校验/构建）应一键化、可 dry-run。
- **决定**：`daily_runner.py` 只做机械链路 + 明确报错；内容生成留在 LLM 会话。runner 是每日会话的**入口与验收器**，不是生成器。
- **复审条件**：若未来出现可靠纯脚本生成路径（如模板化程度足够高）再评估合并。

## ADR-003 测试债范围
- **背景**：存量 pytest 4 失败（weekly_review KeyError 'scenario_review'）+ test_m4_m5_m6 独立跑 1 个状态依赖失败。Q3 无人应答，按推荐执行。
- **决定**：本轮只修 weekly_review KeyError（30min 时间盒）；test_m4_m5_m6 状态依赖失败记账不修。
- **复审条件**：下轮若动 signal_history/state 结构，须先清此债再动。

## ADR-004 理解层校验挂接方式
- **背景**：validate_understanding.py v1（存在性校验）需挂进门禁族；validate_report.py 已 1218 行，直接内嵌风险高；铁律要求门禁总数变化同步所有提数处。
- **决定**：独立脚本 `scripts/validate_understanding.py`，由 daily_runner 的校验阶段与试产流程**串联调用**（validate_report 26 项 + 理解层校验，两者都过才算门禁全绿）。对外提数口径统一为「26 项硬校验 + 理解层存在性校验（runner 串联强制）」，validate_report 26 数不变。v1 范围：teach 槽非空/今日一课节存在/费曼节存在/每推演块含知识锚+成长含义+验证窗口；语义一致性划 v2。
- **复审条件**：v2 语义校验落地时再评估是否合并进 validate_report。

## ADR-005 对外发布本轮不做
- **背景**：Q4 无人应答，按推荐执行。
- **决定**：不公开 repo、不发公众号；护城河先内化，心跳+质量稳定 ≥2 周后再议。
- **复审条件**：心跳连续 ≥10 个工作日且评审连续「值得读」。

## ADR-006 P1-C 落点：采集准入（cleaner 阶段）
- **背景**：v7.1 [G-1] 是验后拦截，第 1 期实付 9 处回填成本；准入前移可消灭回填。
- **决定**：在 multi_source 清洗/入库路径上加文章级 URL 准入判定（域名根/仅斜杠/无路径 → 不入候选池），口径与 validate_report [G-1] 一致；具体文件实现时确认（cleaner.py 优先，gate.py 兜底）。
- **复审条件**：若准入误伤率高（合法文章级 URL 被拒 >5%），复查判定口径。

## ADR-007 调研降级路径（当日子代理配额超限）
- **背景**：4 组 github-researcher 全部瞬间失败（exceed quota limit，1-2s 内），后台调研不可用。
- **决定**：不阻塞主循环：Phase 2 照常推进；阶段边界重试子代理（先试 1 组防再撞墙）；若持续不可用，Phase 2.5 用主上下文 WebSearch 轻量调研（每组 ≤3 次搜索、只消费结果块）+ 链接 WebFetch 抽查补齐，对标报告如实标注「子代理配额受限，主上下文轻量调研」。
- **复审条件**：配额恢复的会话应重新跑完整后台调研校验对标报告结论。
