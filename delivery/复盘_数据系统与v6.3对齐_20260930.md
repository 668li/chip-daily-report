## ④ 根因拆解（5Why → 五类归属）

- **问题 2（误卷金标）**：Why1 用整目录 add→Why2 前轮承诺未执行→Why3 承诺只活在对话记忆、无机械检查点→**根因：commit 流程缺「staged 清单逐行核对」步骤（方案设计问题）**。
- **问题 9（推演三轮弯路）**：Why1 R5 修订来自审查代理→Why2 代理评结构完备性、读者痛点是内容深度→Why3 规范变更无读者确认节点→Why4 间接循环里验证者错位→**根因：读者价值类变更缺「读者本人验证」强制环节（方案设计问题）**。
- **问题 1（检查14 FAIL）**：Why1 自检表写 PASS 机器判 FAIL→Why2 我按「涉及术语」主观判断，机器按关键词匹配→**根因：防抖清单未对齐机器口径（prompt 缺陷/信息输入不全）**。
- **问题 3（tracker 参数）**：未先读 CLI 契约即调用（信息输入不全）。
- **问题 6（停更未发现）**：health_check 只探 HTTP 200 不探内容新鲜度→**根因：健康检查维度缺失（工具能力限制→方案设计可解）**。
- **问题 4/5/9 的回显损坏与搜索限流**：工具能力限制（外部），纪律兜底。

## ⑥ 停止做｜继续做｜新增做

- **停止做**：①`git add <目录>` 整目录——永远精确列文件（已两次证明会翻车）②在读者未直接确认前落「读者价值类」规范 ③拿自检表当机器门禁替身宣布 PASS。
- **继续做**：①写入后 grep 复核（本会话兜住 ≥4 次损坏）②新机制上线当天实弹验证 ③样板先行再落规范。
- **新增做**：①commit 前执行 `git status --short` 逐行核对 staged 清单（固化进生成会话流程）②health_check 增「最新条目日期」维度（10-12 冻结期满首批）③推演写作期执行 v6.3 专项调研（2-4 轮+带源）。

## ⑦ AI 侧专属改进

- 防抖清单补两条机器口径：检查 14=凡主行含术语关键词必贴 `[技术注解: ]`（不等主观判断）；头部元信息必含「≤72h 条目: N」。
- forecast_tracker/任何 CLI：先 `--help` 或读 argparse 块再调用。
- 对齐类会话模板：第一轮问「对象指认+读感还原+满意样本+用途」四件套（本次四问可复用）。
- WebSearch 遇并发限制直接串行化，不重试并行。

## ⑧ 可沉淀知识库条目

1. **间接循环病根**：读者反馈→AI 解读→审查者加固会系统性跑偏；规范变更前先出样板给读者本人确认。
2. **饿浅两根源**：「现状锚点只从本地取」+「要素标签阵列」会把内容压到人人皆知层；深度=系统坐标+叙事裂缝+可证伪下注。
3. **git add 纪律**：整目录 add 是误卷事故的标准成因；提交前 staged 清单逐行核对。
4. **200≠活着**：feed 健康检查必须含最新条目日期维度（TrendForce 停更 3 个月实证）。
