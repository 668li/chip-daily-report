## 0. 全景：一条材料的一生

```
信源(6类) ─→ materials.upsertIn  [唯一入口：身份+修订+时间线]
              ↓ identity_key 判重 / content_hash 修订 / 三段时间线
            prefilter (temperature 0, 三态)
              ↓ BLOCK 短路（无证据强制降级 UNKNOWN）
            score ×2 (temperature 1, 串行, sum≥2×门槛)
              ↓ near? → understand : summarize（护栏后处理）
            analyses 落库（append-only, output jsonb 存全部中间态）
              ↓
            group 归组（串行队列, 批量判定+低置信换模型复核）→ story/fact
              ↓
            hot 热度（48h 窗 × 24h 半衰 × 独立参与者）
              ↓
            report 日报（每 fact 单代表, 导语由模型写, 编号回映过滤）
```

四个 agent 报告里反复出现的同一句话是全仓库的设计公理：**「不确定就显式失败，绝不静默降级」**。未知配置→本轮抓取可见失败；空列表→失败而非「今天没更新」；适配器失配→失败而非回退到菜单；付费请求结果未知→停止而非重发；正文抓不到→`unconfirmed` 而非猜；正文不足 20 字→不写而不是从标题脑补。

## 1. 判重、修订、时间线（`content/materials.ts`、`lib/url.ts`）

**唯一入口纪律**（`materials.ts` 文件头）：「The single entrance for new material from every channel. It owns identity, revisions and the timeline rule, so no entrance can bypass them.」——外部推送 `POST /api/ingest/items` 也走同一条 `upsertIn`，无旁路。

### 1.1 identity_key 四分支（`materials.ts:114-120`）

| 优先级 | 条件 | key 形态 |
|---|---|---|
| 1 | 调用方显式指定 | 原样 |
| 2 | X 帖 | `x:{tweetId}` |
| 3 | 通用 URL | `url:{normalizeUrl}[#fragment]` |
| 4 | 兜底 | `src:{sourceId}:{sha256(url+\x01+title)[:32]}` |

`normalizeUrl`（`url.ts:7-36`）九步：协议白名单（只收 http/https）→ 无条件清 fragment → host 小写去 `www.` → **协议强制升 https**（http/https 归一）→ 去默认端口 → 微信特例 → 删跟踪参数 → 参数排序 → 尾斜杠剥离（根路径 `/` 除外）。

**跟踪参数白名单实测是 22 个字面量 + 1 个 `utm_[a-z]+` 前缀族**（`url.ts:5`，带 `$` 锚所以 `ref` 不误伤 `referrer`）——纠正此前「30+」的说法。**微信公众号特例**：`mp.weixin.qq.com` 只保留 `__biz/mid/idx/sn` 四参数并**整体重建 query**（微信页常带 chksm/scene/from，逐个删会漏）。

**fragment 保留是源级开关**（`url.ts:61-62`）：`normalizeUrl` 无条件清 hash，只有 `keepFragment: true` 时从**原始 URL** 取回，且 `length > 1` 守卫挡裸 `#`。唯一使用方是 `sources/rss.ts:149` 的 `preserveUrlFragment`——为 GitHub Releases 这类「一页多节」源而设。

### 1.2 内容哈希 + 四道闸门（`materials.ts:95-205`）

`contentHash = sha256(collapse(title) ⨁ \x01 ⨁ collapse(body) ⨁ \x01 ⨁ collapse(excerpt))`；标题先截 1000 字符，空标题回退 URL。

四道「不算修订」的闸门，每道都有事故注释：
1. **异源只算发现不算修订**（`:163`）——曾因采纳第二源的标题/摘要导致文章在两源版本间反复翻转；
2. 哈希相同（`:171`）；
3. **无基线哈希的历史导入只补基线不递增 revision**（`:172-181`）——否则一次 import 会让源还在列的所有文章全部重走付费分析；
4. **历史版本回访**（`:182-187`）——与任何历史版本哈希相同即非新材料，防「列表页在两种渲染间轮转」；
5. **`sameBarringLoss` 乱码容差**（`:100-112`）——U+FFFD 连续段塌缩为单哨兵、按码点比较、长度须严格相等、任一侧为哨兵即视同；三个字段全同才判「没变」。

真修订走一条 SQL（`:191-204`）：`revision = revision + 1`（先 `FOR UPDATE` 持锁防并发重复号）+ **`processing_state = 'new'`**——内容一改退回队列头重新付费分析。

### 1.3 三段时间线（`materials.ts:74-83`）

| 字段 | 语义 | 写入规则 |
|---|---|---|
| `published_at_claim` | 源**声称**的发布时间 | 永不销毁 |
| `published_at` | 我们**信**的发布时间 | 无效日期或**晚于发现时间 1h 以上**→置 null |
| `timeline_at` | 排在哪 | backfill 且有可信源时间→用源时间；否则用发现时间 |

`isHistorical`（`:85-93`）：`backfill && (无源时间 || 发现-源时间 > 48h)`。一处判定**三处生效**：排序键、队列优先级（`PRIORITY.history = -2`）、事件图过滤。48h 硬上限且注释绑死 v1 契约的 72h。新源首导限 30 条/12 个月（`collect.ts:129-139`，`firstImport = !cursor.initializedAt`）。

### 1.4 SSRF 双层（`lib/url.ts` + `lib/http-fetch.ts`）

**两个不同口径**是这个文件最精细处：
- `isBlockedAddress`（直连）：IPv4-mapped/compatible、NAT64 WKP `64:ff9b::/96`、**6to4 `2002::/16` 抽出内嵌 IPv4 重新走 IPv4 黑名单**、Teredo `2001::/32` 整体拒、文档段、ULA、link/site-local、组播；解析失败→拒（`url.ts:120`「not an address we understand: refuse」）。刻意放行 `198.18.0.0/15`（本地代理 fake-IP 段）。
- `isInternalAddress`（走代理时）：窄口径，**不含** Teredo/文档段/组播——注释解释：域名交代理解析，本地解析器对被封站点的「毒答案」不代表代理会连去哪（`url.ts:145-150`）。

`assertPublicUrl`（请求前）+ `guardedLookup`（建连时，`url.ts:196-220`，错误码 `EBLOCKED`）**双重检查防 DNS rebinding**；重定向 `redirect: "manual"` 每跳复检；`.cn`/`.local` 不走代理改直连全口径。

## 2. 打分宪法（`editorial/analyze.ts` + `industry/prompts/selection-score.md`）

### 2.1 权重表（全仓库最核心 KnowHow，109 行提示词；**权重表只存在于提示词，TS 侧没有任何实现**——`attentionScore` 仅出现在 Zod schema、指令文本和取值三处）

| 内容类型 | sig | nov | cred | reson | act | 和 |
|---|---:|---:|---:|---:|---:|---:|
| model_release | 3 | 2 | 2 | 2 | 1 | 10 |
| product_launch | 2 | 2 | 1 | 2 | 3 | 10 |
| tool_or_prompt | 1 | 2 | 1 | 2 | 4 | 10 |
| research_paper | 5 | 3 | 1 | 0 | 1 | 10 |
| industry_event | 3 | 1 | 2 | 4 | 0 | 10 |
| opinion_analysis | 1 | 3 | 1 | 4 | 1 | 10 |
| tutorial_explainer | 1 | 1 | 1 | 3 | 4 | 10 |

`attentionScore = Σ(轴 × 权重)`，每行和为 10 故结果天然落在 0-100。四条禁令（`:54`）：不许先求平均、不许改权重、不许堆多个普通理由凑高分、不许为靠近门槛改结果（防 score hacking）。

**轴间去相关**是显式约束（`:34-38`）：cred「不是来源名气」、act「纯新闻 act 低是正常的，不应反过来抹掉 sig」。

**噪声上限 9 条**全带数值：客户案例 PR `sig≤4`、例行小版本 `sig≤3`、营销软文 `sig≤2`、纯预告 `nov≤3 且 cred≤4`、单用户「惊艳」体验 `nov≤3 且 sig≤4`、摘要合集 `sig≤3`、厂商绑定 how-to `sig≤3`、底层小改进 `sig≤4 且 reson≤3`、宏大观点/趣闻「明显低分」。

**事件口径校正节**（`:99-109`）是**文末 override**，显式声明「不改五轴定义、类型权重和单字段输出契约」，并**显式撤销**了前面两条上限（短引用不得按「个人二手体验」压低 sig；开源 Harness 不得套「客户案例 PR」上限）——追加式 override 放文末以吃 recency 优势，同时防 override 引发连锁偏离。

### 2.2 盲评：信息隔离是最硬的约束

`buildScoreInput`（`analyze.ts:87-103`）**只注入三样**：发布时间、原标题、完整正文（上限 60k 字符）。`source.tier` 只用于查门槛（`:344`），**从不进 prompt**；提示词 L13 明令「不要猜这些信息，也不要把大厂、名校、长正文、术语、数字很多或 SOTA 当成自动加分项」；`ScoreSchema` 只允许一个字段，Zod 默认剥离未知键。提示词 L16/L92 禁输出五轴/置信度/精选结论——工程侧因此也无从复算权重。

### 2.3 双评分：唯一 temperature 1 的地方

```ts
// analyze.ts:59-66 —— 全流程唯一 temperature: 1
const SCORE_CALL = { "glm-5.3-flash-selection": { temperature: 1, maxTokens: 65_536, timeoutMs: 180_000 } };
const scoreCall = (m) => SCORE_CALL[m] ?? { temperature: 0.2, maxTokens: 1024, timeoutMs: 120_000 };
```
prefilter=0、structure/understand/summarize=0.2。`-selection` 预设与普通 GLM **同一底层模型**，差异只在 `reasoning_effort: low→high`、`clear_thinking`、`top_p: 0.95`（`providers/llm.ts:31-52`）。`top_p` 与 `temperature` 并存是刻意的：靠 0.95 保留多样性、靠 1 保留采样熵。

两次**严格串行**（第二次复用 provider prompt cache 摊薄成本），输入字节相同，差异纯来自采样；`attemptTag: score-1/score-2` 让两次成为**两个独立付费回执**——同 tag 会被回执复用直接回放，拿不到第二个独立样本。

**判定**（`:376-380`）：
```ts
const sum = values.reduce((t, v) => t + v, 0);
const score = Math.floor(sum / SCORE_CALLS);        // 展示分，floor 刻意向下
const selected = relevance === "pass" && sum !== null && threshold !== null && sum >= threshold * SCORE_CALLS;
const near = sum >= threshold * SCORE_CALLS || sum > UNDERSTAND_FLOOR * SCORE_CALLS;  // 注意 near 是严格大于
```
**用方差替代置信度**：两次分差越大说明模型越不稳定，而代码只取和、**不把分差写进任何字段**。测试断言 `78 + 72 = 150 >= 120`（T2 双次均分 75 ≥ 60×2 的等价形式）。

### 2.4 prefilter 三态 + 代码强制降级

提示词侧三态：`PASS`（实质 AI 相关）/ `BLOCK`（**需能确认无关的正面依据，不能仅以「未提及 AI」为依据**）/ `UNKNOWN`（材料不足，保留待补）。schema（`:107-110`）做 trim+大写化，`reason` 用 `.catch("")` 解析失败不阻断。

**三层处置全在代码**：
1. `analyze.ts:209-211`——模型判 BLOCK 但 `missingEvidence(a)` 为真（无正文/无摘要/无 X 帖文本）→ **强制降级 UNKNOWN**；
2. `:342-343`——只有 BLOCK 短路返回，UNKNOWN 与 PASS 同路；
3. `:373`——过了预筛但没产出可用中文标题+摘要 → `relevance='unknown'` 挂起（不是丢弃）。

落库 `relevance` 三态（`0001_core.sql:181`）；`processing_state` 只有 `analyzed`/`blocked` 两态由分析写；公开池裁决 `isPoolEligible` 要求 `participationMode==='editorial' && relevance==='pass' && 有标题 && 有摘要`。

### 2.5 refused 与 analyses 落库

`refused`（智谱 1301 内容过滤，`:177` `isContentFilter`）**中途立即返回不补跑**→ `values=null` → selected 必 false（**fail-closed：拒审≠入选**），落 `output.scoreRefused=true`。

`analyses` 是 append-only 表（`0001_core.sql:173-193`），`output` jsonb 存 7 个可选键：prefilter{label,reason}、scores（两次原值）、scoreModel、threshold、scoreRefused、writer/writerModel/itemType/authorRole、identityGuard（**仅 fallback 时**）、fact。`prompt_version` 存聚合哈希而**逐条 receipt 存单项版本**——调评分提示词时能精确区分哪一步变了。stale revision 结果照写不误（可追溯）但不更新 processing_state（`:438-449`）。

## 3. 事件聚簇（`events/group.ts` 864 行 + `relate.ts` + `merge.ts` 35 行）

### 3.1 十七步主流程（`decide()` 编排）

人工优先查 → 历史短路 → 非 editorial 走 signal 路径 → 既有归属保留 → 同 URL/回复引用旁路 → 召回 → **批量判定** → 低置信**逐对复核** → 规则收口（ROOTUP 独立 / 进展挂根 / 新故事）→ **行锁内二次人工查** → 建 story/fact → 写成员/信号/决策记录 → 事务外补发页面。

**两条零模型旁路**：同 URL 直接 `verdict="same-url"`（`:663-666`）；X 回复/引用的帖所属 fact 以 `boost score=1` 强制进候选（`:232`）。

### 3.2 三方问法的实测依据（本仓库最有说服力的注释，`relate.ts:1-10`）

> Asking for the three-way relation with both reports fully described is what makes the judge usable: **a yes/no question with "prefer no" refused half of the true merges (measured 2026-09-28 on 370 labelled pairs).**

他们**先标了 370 对样本**才敢定判定问法——这正是 SelectBench 精神的直接体现。

### 3.3 阈值全表

| 常量 | 值 | 用途 |
|---|---|---|
| `RECALL_DAYS` | 14 | 召回窗口（按**发现**时间，旧页今天发现也能遇同伴） |
| `RECALL_MIN_COSINE` | 0.6 | 进候选 |
| `CONFIRM_BELOW_COSINE` | **0.85** | 低于此且判 SAME_OCCURRENCE → 换 `groupReview` 复核 |
| `TIE_MIN_CONFIDENCE` | 0.8 | 「firmly tied」 |

### 3.4 consolidate 双向复核（**在 group.ts:490-520，不在 merge.ts**——此前认知有误）

锚点=最早故事；第一轮 `group` 判 A→B（门槛 0.8，不过直接短路省第二次调用）；第二轮 **`groupReview` 且方向反转** 判 B→A（门槛降到 **0.75**）。0.75 的定标依据（`relate.ts:153-158`）：370 对参考集上故事级 P=0.944 R=0.962 @0.75，对比 0.8 的 P=0.964 R=0.896；170 个真实根 fact 对上新增合并读起来都对。

`mergeStoryInto` 幂等（已合则什么都不改）、信号去重迁入、`story_aliases` 收旧 public_id（读路径 308）、事务外重发页面+入队 digest+写审计。

**story_links（相关事件）要求 ≥2 篇报道同时牵连**（`RELATED_MIN_REPORTS=2`），注释：「A single tie is too often a stray answer about one candidate among many」；且**多话题盘点起头的故事不合并也不互链**。

### 3.5 人工永远赢

`manualDecision` 查两次（模型调用前零成本返回；**行锁内再查一次**——注释：模型作答期间的人工 detach 赢）；`manual` 列还通过 `trusted()` 参与证据资格（8 处调用，人工成员永远算证据）；`resetAutomatic` 只清 `NOT manual` 的成员。`regroup_pending` 的报道在重新判定前**不算他人证据**，且判定失败时保持 pending（重试时重新判）。

## 4. 热度（`events/hot.ts`，rule `heat-v1-48h-halflife24h`）

```sql
WITH obs AS (  -- 48h 窗内，每 (story, participant) 取 max(observed_at)
  ...
), agg AS (
  SELECT story_id, count(*) AS participants,
    sum(power(0.5, hours_since/24.0)) AS heat,            -- 24h 半衰
    sum(...) FILTER (WHERE NOT behind) AS heat_obs,         -- 公平性修正
    ...
)
SELECT ... WHERE participants >= 2 AND editorial_participants >= 1
```
- `participant_key`（`group.ts:77-79`）：`signal_group_id` 存在则 `group:{id}`，否则 `source:{id}`——**同一信源组只算一个参与者**；`GROUP BY + max(observed_at)` 保证重复采集不加热。
- **公平性修正**：抓取落后（超 3 个周期且至少 90 分钟没成功）的源，其参与者单列 `heat_obs`；与 6 小时前对比**只用全程被观测的参与者**——「某源没抓到」不被误判为「热度变化」。历史小时快照 `complete=false` 会用 `grace=false` 口径修复重算。
- 徽标：`surge`（6h 新参与者≥3 且≥50%）、`new`（首报<6h）、`rising`（非 surge 且涨幅>15%）、`trend up/down`（±10%）。
- **发现一处小瑕疵**（agent 记录）：`trend:"new"` 用 `prevAll` 口径而 `pct` 可能来自 `heat_obs` 口径，两者不完全一致。
- 榜单排序：T1 > T1.5 > T2（`hot-read.ts:31-36`），单故事最多露 6 个面。

## 5. 写作与护栏（`editorial/writing.ts`）

**降级阶梯四档**（`analyze.ts:299-333, 353-356`）：`understand`（近选且未被内容过滤）→ `summarize`（默认）→ `verbatim`（短帖已是中文，**零模型调用**）→ `none`（非短帖正文<20 字，**不从标题脑补**）；`runUnderstand` 返回 null 时 `??` 自动落回 summarize。模型不支持视觉→只送文本；模型拒绝这张图→去图重试（同一回执不计新付费）。

**IdentityGuard（代码级防张冠李戴）**：允许集 = ①`IDENTITY_LEXICON`（31 家公司 × 多正则）在标题/正文/引用/来源名中的命中 + ②上下文别名 + ③`PUBLISHER_DOMAINS` 发布域映射（11 组，GitHub/arXiv 刻意不算发布方）+ ④信源属主实体。
- `surfaceVariants`：`GPT 5.5`↔`GPT-5.5` 双向兼容，否则翻译换连字符会误判「引入公司」；
- 发布域匹配用 `host===d || host.endsWith('.'+d)`——**防 `evilopenai.com`**；
- **不对称降级**：标题违规→回退原中文标题（外文标题置空，**绝不用模型写的**）；摘要违规→整体置空；两者独立执行；`outcome` 取或；**无二次修复调用**（护栏失败就降级，不烧钱）。

**长度规则与三级压缩**（`writing.ts:235-263`）：`answerFirstSummaryLengthOk` = ≤200 字 + 原文≥500 时 80-200/2-3 句、否则 50-200/≤3 句（`sourceLength` 用清洗后净长，URL 不充数）；不达标走 `compactAnswerFirstSummary`：句级切（190 上限，80 停）→ 子句级切（逗号/分号/顿号处，**「never inside a name or number」**）→ 连 50 字都拼不出就**返回原文**（宁不合规不残缺）。

**`cleanArticleTextForLLM`** 十步清洗，注释点破真因：删 `https?://\S+` 是因为「**URL 的 /2025/ 路径 models took for years**」把它当年份。提示词第 7 条（相对时间照抄绝不换算年份）与代码侧删 URL 是**双保险**。

**四类共享规则**（`industry/prompts/rules-*.md`，唯一被多提示词 include 的层）：
- `anti-hallucination` 9 条，第 8 条「不得强化语气或范围」（「多项研究未发现」≠「没有研究」）、第 9 条排他性表述须原文明确——**这两条正是我们「五守则」的第 4/3 条来源**；
- `self-contained-title` 第 5 条最长：How/Why/Guide/Analysis/Review/Benchmark 类标题**必须保留文章类型**，不能改成「发布/推出/上线/开源」；第 4 条给上位词兜底（"开源多模态模型"）——**不编造**与**不能什么都不写**之间的中间地带。**这就是我们「标题保型」守则的出处**；
- `answer-first-summary` 5 条，动机是「让第一句可被搜索与 AI 独立引用」（喂 RAG 的自洽语料）；
- `domain` 4 节：17 个歧义词各带显式反例（LLM≠法学硕士）；版本号「一字不改」附反例（不要把 405B 译成 4050 亿）；精确区间不得改写成模糊数量词（$10B-$100B≠数百亿至数千亿）。

提示词装配只有 `{{name}}`/`{{> file}}` 两种语法，**缺值报错不静默空白**，版本=内容 SHA256 前 10 位。`identity-context.md` 注入时第二句是双向护栏：发布域=OpenAI **不代表**文章必是 OpenAI 产品发布。

**配置白名单强校验**（`collect.ts:99-101`）：填了该 kind 不实现的配置键 → **本轮 fetch 可见失败**，绝不静默退回通用解析。

**分级三维的消费点**：`tier`→门槛+精选资格（EXCLUDE_MP 硬编码不可 override 绕过）；`participation_mode`→采集段（detail 抓全文/teaser 仅 editorial）、内容段（signal 跳分析直接归组）、发布段（`isolated`→`withdrawn` 连详情页都没有）；`first_party`→每事件唯一 primary 选举+代表报道排序。

**双重全文许可是二阶门控**（`rules.ts:42-53`）：`mayRedistribute = syndicate_fulltext && bodyMode==='full'`，而 `bodyMode` 又依赖 `site_fulltext`——**三重条件**。两者默认全关（`0036` 把 `site_fulltext` 默认值从 true 改为 false），18 个示范源**全部显式写 false**。

**X 分片的 `coveredTo` 破解**（`collect.ts:210-225`）：`max(自身 lastTweetId, 上次成功检查时间-10min 折算的 snowflake id)`，分片取 **min**——用 Snowflake 时间戳把「上次成功检查」折成 id 边界，解决冷门账号 id 极旧拖垮整个分片的问题；分片 key = sourceId 排序后 sha256 前 12 位（稳定分片，增删一源只影响其后的分片）。

**频率自适应**（`collect.ts:339-363`，每天 04:20）：`target = 1440/(perDay×3)` 夹在 `[min,max]`；上限表——免费 editorial 60min / x_search 或付费列表 120 / hot_signal 180；付费列表下限 60（防烧穿 Jina 日预算）；沉默源（perDay≤0.15）直接给上限。**失败退避**：`LEAST(interval×(fail+2), 360)`，**预算熔断固定 15 分钟且不计失败次数**。

## 7. 队列、回执、预算（`jobs/` + `providers/receipts.ts`）

**11 条业务队列 + cron.* 单例**；`events.group` **localConcurrency:1 串行**（注释：同一新事实的两篇报道不能都创建它）。

**优先级三档**：`live 0` / `liveSignal -1` / `history -2`——「新源首导或回灌永不拖住今天的新闻」。

**两套重试**：pg-boss 层（进程崩溃后重放）+ 业务层阶梯 `[5,10,20,40,60,120,240,360]` 分钟。失败四路分流：停机/部署→重抛**不消耗次数**；回执忙/预算熔断→定时重排**不消耗次数**；不可重试拒答→立即 failed；模型输出坏→最多 3 次；其余走阶梯。抽取 3 次失败后 `body_status='unconfirmed'`（注释：*"unconfirmed" body, never a wrong one*）仍送分析。

**优雅停机**：`shutdownSignal` 在每个分析阶段间检查，在飞的付费调用允许收尾，`STOP_TIMEOUT_MS = 195s = 最长单次付费调用 180s + 15s 余量`。

**回执状态机**（全仓最精巧的可靠性设计）：
```
pending ──调用──▶ received ──业务写完──▶ completed
   │                  │
   │明确拒收           │不可用
   ▼                  ▼
 failed ◀──────────────┘
   │ 超时/连接重置/崩溃（钱可能已花）
   ▼
unknown ──ops.recover 30 分钟后自动放行一次──▶ failed（+ 文章直接回队列）
        └─ 已放行过一次仍 unknown → 只进每日 09:00 系统日报，等人工
```
- `logical_key = service:purpose:model:sha256(identity):attemptTag`；LLM 的 identity 六元组（model/promptVersion/sha256(system)/sha256(user)/temperature/maxTokens/extra）；
- 认领在事务内 `pg_advisory_xact_lock(hashtext('budget:'+service))` **先锁后查预算**——并发不会超发；
- 预算计的是 **attempt**（`receipt_attempts` 表，origin='live' 过滤），「重试不能从预算溜过去，早先计费的回答不被后来的覆盖」；
- **unknown 只放行一次**的实现很巧：`NOT EXISTS (... error LIKE '自动放行：结果未知超过 30 分钟%')` + `WHERE status='unknown'` 条件 UPDATE（并发安全）；放行时一并把卡住的文章 `processing_state` 回 new 直接重排。

## 8. 校准闭环（`scripts/eval-selection.ts` 167 行）

**gold 样本是 JSONL 文件不是表**，`GoldRow` schema：`caseId / material{title,originalTitle,publishedAt,sourceName,bodyZh,bodyOriginal} / sourceFacts{sourceKind,sourceTier,firstParty,language} / samplingContext{benchmarkSplit,samplingStratum} / gold{decision: select|reject|either}`。

**复跑方式不 mock，直接 import 生产模块**：`runAnalysis(toInput(r), { scoreModel: model, stages: "selection" })`——同一份 `SCORE_SYSTEM`、同一份 `SCORE_CALL`、同一份 `PrefilterSchema`；`stages:"selection"` 在评分后短路跳过昂贵写作。`bodyStatus:"ok"` 硬编码绕过 `waitsForPage()`，保证样本一定进评分。

**指标**：`accuracy/precision/recall/f1/selectedRate/goldSelectRate` + `either` 单独计数不计入分母；**`selectedRate` 与 `goldSelectRate` 的差 = 系统性偏松/偏紧的量化**。FP 记模型理由、FN 记 relevance——对应 docs/selection.md 的三类归因（该选没选→写进「必须正常评价」；不该选却选了→写进「必须压住」；整体偏松偏紧且错题贴门槛→才动门槛）。

**门槛扫描 40-90 步长 2** 共 26 点，判定式与生产一致。确定性抽样用 LCG（`*1664525+1013904223`）自实现洗牌，同 seed 同样本——跨版本可比。`meta.promptVersion` 写聚合哈希，是「每一版评分标准可比」的锚。**重跑免费**（回执复用），只有改过的部分产生新调用。

**docs/selection.md 的方法论原文**（最该抄的一段）：「多放**难例**：差一点就该选、差一点就不该选的。一眼就能判断的放太多，准确率会虚高」+「分出一部分做**留出集**，调提示词只看开发集，免得把提示词调成只会做这几道题」+「标注的人最好就是以后读这个站的人」+「**先改标准，再动门槛：门槛只能整体移动，解决不了哪一类判错了**」。
