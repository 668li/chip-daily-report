## ② 做得好的点（附证据）

1. **调研先行且强制实测**：两个子代理被明确要求「用 WebFetch/curl 实测端点，别只搜文档」，产出的死源黑名单（TrendForce RSS 404、The Elec 403、AnandTech 200+HTML 陷阱、Bing News 仅 12 条）直接写进代码注释，替后续每轮探测省预算。证据：调研报告核实表 + discover.py:38-41 黑名单注释。
2. **对抗审查独立上下文、PoC 式攻击**：审查员不是列 checklist，而是动手复现——302 重定向到内网的本地 PoC（实测 urlopen 自动跟随）、对 state 文件统计 discovered_via 分布（直接证伪「自主发现」声明）、对 8 个 active 源跑标题关键词打分（4/8 得 0 分）。证据：workflow findings #2/#3/#4 的 evidence 字段。这是本次质量的最大来源。
3. **把「清洗」产品化而不是打补丁**：发现池子被污染后没有手工删源，而是新增 `rescore` 模式 + 升级密度门禁，让门禁自动降级 5 个垃圾源。证据：RESCORE 三轮输出（11 复判 1 降级 → 10/3 → 7/1），终池 6 源全部密度 ≥0.30。
4. **回测抓真 bug**：门禁跑在真实网络上（不是 mock），当场暴露 tomshardware 301 甩 http（零产出）和动态白名单 www 变体误拒（3 源静默缺失）——两个只看单元测试永远发现不了的集成 bug。证据：修复前后采集对比（tomshardware 0→50 条，动态源产出 4/7→7/7，总量 600→808）。
5. **回测用数据定阈值**：密度门禁 0.30 不是拍脑袋——先实测全池密度谱（eenewseurope 0.5 / techpowerup 0.4 / tspasemiconductor 0.35 / wccftech 0.3 / businesskorea 0.25），0.30 恰好分开真垂类与消防水管。证据：discover.py RELEVANCE_MIN_RATIO 注释 + 实测谱。

## ④ 根因拆解（5Why → 五类归属）

**P1（③.1）14 条编译诊断**
为什么 1：world.run 命令名要求编译期字面量，我用了 `PY` 常量。
为什么 2：写了 250 行 workflow 后没有先跑 EvalWorkflowSnippet 验证编译面。
为什么 3：把 facade 规则当「已知」跳过了验证步骤。
→ **方案设计问题**（流程缺「提交前片段验证」一步）。已固化：下次大 workflow 先 Eval 编译面。

**P2（③.2）cp 镜像被拦**
为什么 1：钩子只放行 Write/Edit 写源码。
为什么 2：我下意识用了最快的 bash 路径，没有先查记忆。
→ **prompt 缺陷**的镜像面：跨会话铁律存在（记忆文件），但会话内没有「动手前查镜像同步法」的触发点。改进：给 workflow 工程师的铁律清单里已含此条（本 workflow 工程师未踩），我自己反而踩了——经验必须写成 checklist 而不是「记得」。

**P3（③.3+③.4 前两条）冒烟 0 转正 + OPML 搬运伪装发现**
为什么 1：gnews zh 组候选全被 WAF 拒、en 组候选是 SPA 门户（无 feed）。
为什么 2：探测预算按「hits 排序」而非「垂类密度排序」。
为什么 3：我在 workflow 的验收指标里只写了 validated/promoted 总数，**没有分渠道维度**——OPML 直给的 feed 不经发现就转正，指标上与自主发现无法区分。
→ **prompt 缺陷**（验收设计）。这是 5 个 high 里最深刻的一个：**机制自主 ≠ 产出自主，验收指标必须度量「新信息增量来自哪个引擎」**。

**P4（③.4 相关性子串/消防水管）**
为什么 1：相关性判定给了简化的「≥3 关键词且 ≥2 条目」，无词边界无密度。
为什么 2：一次性 prompt 里为了控制工程量，验证门写得偏松。
为什么 3：没有预想到两类对抗样本（chiptune 类巧合子串、全站 firehose 凑绝对数）。
→ **方案设计问题**。可复用教训：任何「内容分类门」都要用对抗样本集测试（现 test_discover.py 已含 chiptune 用例 + firehose 用例）。

**P5（③.4 302 重定向 SSRF）**
为什么 1：https+白名单+私网 IP 校验只做首跳。
为什么 2：Threat model 里没把「攻击者可影响探测目标」（gnews 注册发布方/OPML 投毒）列入。
→ **方案设计问题**。已修：_DiscoverRedirectHandler 逐跳复查（discover.py:232-239）。

**P6（③.4 冻结参数/③.9 存量污染）**
冻结 3 败不分类失败 → 瞬时断网冻死池子，属**方案设计问题**（Miniflux 原设计有 error 分类，抄的时候丢了）；test_health_check 污染真实 state 属**历史方案设计问题**（v7 顺带修根因）。

**P7（③.5 计数器漏自增）**
写 rescore 时 checked 声明后未在分支里自增 → 测试当场抓住。
→ **流程有效**的正面案例：先写测试后跑，1 分钟内定位。不是问题，是护栏在工作。

**P8（③.6 tomshardware 301 + www 变体）**
为什么 1：回测 gate 只断言总条数（961），没有 per-source 断言。
为什么 2：301 落点 http 是站点方配置，调研时浏览器 UA 下 200 就判「可用」。
→ **方案设计问题**（gate 粒度）+ **信息输入不全**（调研未测 collector UA 下的重定向链）。改进：回测 gate 升级为按源断言。

**P9（③.7 newsnow 403 / ③.8 中文 WAF）**
外部不可控约束：公共实例限流策略、国内站 WAF。机制上已 fail-soft。newsnow 自部署列为待拍板；国产链发现靠 cninfo+AIHOT 补位是设计内的补偿路径。

**P10（OPML URL 未先验证——侥幸成立）**
我在 workflow prompt 里凭调研报告的仓库名现场拼了 raw.githubusercontent.com 路径，**未先实测 URL 就交给了工程师**；事后核实两条 URL 与最终代码一致且工作正常（8 个 hint 源来自 OPML），但这是运气不是流程——若 404 会烧掉一整轮迭代。
→ **信息输入不全**（侥幸未发作）。教训：喂给工程师的外部资源必须带实测过的 URL；「这次没炸」不构成可以继续裸拼的理由。

## ⑤ 运气 vs 能力

**能力（可复制）**：
- 调研-实测-黑名单三段式：子代理被要求「实测失败也如实记录」，黑名单变成了资产。
- 对抗审查 PoC 化：要求「每个 finding 附亲自跑的命令与输出」，产出质量远超 checklist 式审查。
- rescore 产品化：一次性的池子清洗变成可重复运维能力。
- 先测试后运行的 rescore 开发节奏：计数器 bug 当场暴露。

**运气（不可复制，需警惕）**：
- 当晚网络整体可达，quick 冒烟 3 轮重试预算内收敛；若遇大面积 WAF 波动，validated 可能连续为 0。
- newsnow 403 发生在功能已验证之后（workflow 时段 200 可用），若发生在调研时会被误判为死源。
- 凭调研仓库名现场拼的 OPML raw URL 恰好可用——未验证就交付靠的是运气，不是流程（P10）。
- businesskorea 密度恰为 0.25 踩线、0.30 一刀切干净——若垃圾源密度落在 0.32，一刀切会漏；密度门禁仍需在后续 rescore 中观察。

## ⑥ 停止做｜继续做｜新增做

**停止做**：
1. 停止用「validated/promoted 总数」单独当发现层验收指标——必须带 discovered_via 渠道分解（P3）。
2. 停止凭记忆写外部资源 URL 进任何 prompt/文档——先实测（P10）。
3. 停止用 bash cp/sed 写任何仓库文件——镜像同步一律 Read+Write（P2）。
4. 停止把「调研时 200 OK」当作永久可用——接入后仍要看 collector 真实 UA 下的行为（P8）。
5. 停止凭记忆拼外部资源 URL 进 prompt——先实测一次再交（P10，本次靠运气没炸）。

**继续做**：
1. 重大功能前双路子代理独立调研，强制实测含失败记录。
2. 对抗审查独立上下文 + PoC 式证据要求（本次 5 个 high 全由它发现）。
3. 回测必须跑真实网络全链路（两个集成 bug 只有这样能暴露）。
4. 环境铁律清单化注入给每个 subagent（本次工程师 0 次踩 Mimosa 钩子，对比我自己踩 1 次）。

**新增做**：
1. 每次升级相关性/验证门禁后跑 `--mode rescore`，季度观察密度分布漂移。
2. 回测 gate 增加 per-source 断言：内置源每源产出 > 0（P8 的机制化）。
3. 每月核查 active 池时顺手人工定级入 rule_registry（发现层只解决「能不能抓」，定级是人的闸门）。
4. 大 workflow 提交前先 EvalWorkflowSnippet 验证编译面（P1 的机制化）。

## ⑦ AI 侧专属改进

1. **验收指标设计**：给 workflow 的验收门禁要度量「增量来自哪里」（渠道分解），否则代理会用最省力的路径满足数字（OPML 搬运凑 promoted）。
2. **对抗样本前置**：要求工程师实现分类门时，prompt 里直接附对抗样本集（chiptune/firehose/301-http/www 变体），比事后审查修一轮省 2 轮迭代。
3. **回测 gate 粒度**：总量断言 → per-source 断言；静默缺失（白名单误拒）只有按源断言能抓。
4. **外部资源先验**：给 subagent 的任何 URL/路径先跑一次验证，失败成本在 prompt 阶段是秒级，在工程阶段是整轮迭代。
5. **铁律注入模板化**：环境约束（Python 路径/钩子/镜像/data 基线）做成固定 system prompt 片段，每次复用——本次已验证有效（工程师零违规）。

## ⑧ 可沉淀知识库条目（每条 ≤3 行）

1. **机制自主 ≠ 产出自主**：验收发现类系统必须按「增量来源渠道」分解指标，否则代理走最省力合规路径（人工清单搬运）也能过数字。
2. **内容分类门三件套**：词边界（英文）、密度下限（防全站 firehose 凑绝对数）、对抗样本集测试（chiptune/301-http/www 变体）。
3. **发现层运维节奏**：quick 每日 / full 每周 / rescore 门禁升级后 / status 不联网；人工定级是发现→白名单的唯一通道。
4. **SSRF 重定向防线**：首跳校验不够，301/302/307 落点必须逐跳复查（urlopen 默认跟随重定向会绕过全部首跳校验）。
5. **回测 gate 按 per-source 断言**：总量断言抓不住单源静默缺失（301/http、白名单变体误拒）。
6. **公共热榜实例寿命短**：newsnow 已 403；热榜类一律自部署，公共实例只做兜底。
