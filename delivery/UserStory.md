## 1. 业务背景与价值

### 1.1 业务背景

**当前业务现状**：chip-daily-report 是一套模块化 Markdown 技能（1 份主控 `SKILL.md` + 3 份 references 知识库 + 1 个 768 行 Python 校验脚本 `scripts/validate_report.py` + 1 份 Agent YAML + 1 套 TRAE 镜像），类型为「P4 产物生成型 · v5.0 专业深度版（微电子视角 + 技术解读 + 产业链关联）」。现状只能由人工触发词手动启动 6 步流程，已产出 3 期日报：D9（11 条）、D10（9 条）、D11（22 条）。服务对象为微电子专业读者与内容运维团队，属于内部专业内容生产工具，无直接营收。

**触发本次需求的事件**：v5.0 升级后暴露三类结构性问题，成为本期立项的直接动因：

- **规则口径在「文档 / 脚本 / 镜像」三处分裂**：根目录 A 级域名 33 个 vs `.trae` 镜像 21 个，净差 12 个；同一份 D11 的 22 条来源按根目录清单判 A 级占比 72.7%、按镜像清单判 40.9%，相差 31.8 个百分点；共识别出 16 组规则冲突（X1–X16）。
- **全流程无调度、无可观测**：唯一运行方式为触发词手动启动，失败信号只有脚本退出码 0/1，无日志留存、无重试、无历史指标，运行全程依赖人工在场（每期约 10 分钟）。
- **质量门禁只守格式不守语义**：`validate_report.py` 的 15 项检查均为正则与计数类检查，摘要是否忠实于来源、技术注解是否解释正确、分类是否真的正确均无自动校验；D11 出现"氧化镓正文配碳化硅注解"的错配。

**本系统在产品矩阵中的位置**：在「芯片行业情报供给」价值主线中承担**每日事实层供给与质量把关**职责，向上承接公开检索与 LLM 推理底座，向下为专业读者、产业链分析读者与归档检索提供标准化产物；与规则治理中心、运行看板共同形成完整业务闭环。本系统不承担情报的解读、估值与投资决策职责。

### 1.2 行业方案

> 同类功能、痛点的行业标杆系统及解决方案（事实与对比承接 `research_report.md`，G2 已通过）。

| 标杆系统 | 厂商 / 来源 | 场景覆盖 | 技术亮点 | 商业模式 | 适用度 |
| --- | --- | --- | --- | --- | --- |
| B1 Perplexity（含 Sonar API） | Perplexity AI | 实时联网问答、深度研究、带内联引用的报告生成 | RAG 管线 + 逐句引用锚定 + 多模型编排 + 实时检索 | SaaS 订阅 + API 按 token 计费 | 低（范式可参考，组件不可用） |
| B2 LangGraph | LangChain 社区（MIT） | 有状态、多步、含分支与循环的 Agent 编排 | StateGraph 状态机 + Checkpointer 持久化 + 人工介入中断 | 开源，可自托管 | 高 |
| B3 DeepEval | Confident AI 社区（开源） | LLM 输出单元化评测（幻觉 / 忠实度 / 摘要质量） | Pytest 原生 + G-Eval 评委 + 50 余项指标 + 确定性代码评估器 | 开源，可自托管 | 中 |
| B4 Prefect | Prefect 社区（Apache 2.0） | Python 工作流编排、定时调度、可观测、可恢复执行 | flow 装饰器 + 持久化状态恢复 + 事件驱动 + 数据不出域的混合执行 | 开源，可自托管 | 高 |

**选型落点**：编排层选 **LangGraph**（完整版启用状态机，MVP 先以顺序流程跑通）；运维层选 **Prefect Server 自托管**；质量层保持 `validate_report.py` 为硬门禁执行权威，DeepEval 式语义层在完整版以"先记录不拦截"方式灰度接入；来源分级与防幻觉沿用本项目既有 A/B/C 域名规则，不引入外部锚定服务。**不借鉴 B1**（闭源 SaaS、数据出境，合规可控性低）。

## 5. 用户旅程（UserStory）

> 每条 UserStory 按 5.x.1 ~ 5.x.7 七个维度展开：业务场景 / 业务流程 / UE 原型 / 业务逻辑 / 数据描述 / 验收标准 AC / 外部集成接口。US 覆盖 MVP 全部 P0 功能（F1–F8、F14）与完整版功能（F9–F13、F15），并覆盖 6 类角色。

### 5.1 US-1：技能维护者维护单一权威规则注册表（F1）

#### 5.1.1 业务场景

- **视角**：技能维护者
- **描述逻辑**：每周复盘或规则修订时，技能维护者需要修改来源分级、Rubric 项或分类仲裁条款。过去这些规则散落在 sources.md、rubric.md、classification.md 与脚本常量四处，改一处漏三处（X1/X7 已证：根目录 33 域名 vs 镜像 21 域名）。现在规则集中为一份机器可读注册表，技能维护者只改一处，系统单向生成三处副本。

#### 5.1.2 业务流程

- **Given** 技能维护者打开规则治理中心的单一权威注册表编辑界面；
- **When** 技能维护者修订 A/B/C 域名分级清单或 15 项 Rubric 定义或分类仲裁条款，并点击"生成并同步副本"；
- **Then** 系统从注册表单向生成 sources.md、rubric.md、classification.md 与脚本域名常量，三副本内容保持一致，并给出生成结果摘要。

#### 5.1.3 UE 原型

MVP 形态为命令行加本地静态复核页：

```
规则治理中心 · 注册表编辑
├─ A/B/C 域名分级清单（机器可读 YAML/JSON，按 X1/X7 合并后的 33+5 域名）
├─ 15 项 Rubric 定义（编号与项目名按脚本口径，X5 裁决）
├─ 分类仲裁条款（X9/X10/X11 裁决落地）
└─ 操作：编辑 → 校验语法 → 生成三副本 → 查看生成 diff
```

#### 5.1.4 业务逻辑

1. 注册表为唯一权威数据源，领域规则资产 100% 复用现有 references 内容，仅对 X1–X16 裁决命中条款定点修订；
2. 单向生成逻辑：注册表 → 模板渲染 → sources.md / rubric.md / classification.md / `A_LEVEL_DOMAINS` 常量；
3. 生成后自动附带 diff 摘要，供技能维护者确认无意外变更；
4. 生成结果进入 F2 一致性校验流程（US-2）作为提交前置。

#### 5.1.5 数据描述

| 数据项 | 来源 | 流向 | 说明 |
| --- | --- | --- | --- |
| 注册表规则 | 技能维护者编辑 | 注册表文件 | 唯一权威源 |
| 三副本文件 | 注册表单向生成 | sources.md / rubric.md / classification.md / 脚本常量 | 与注册表保持一致 |
| 生成 diff | 生成动作 | 复核界面 | 供确认 |

#### 5.1.6 验收标准 AC

- **AC-1（正常路径）**：Given 注册表含 X1 裁决后的 33 个根目录 A 级域名，When 技能维护者触发"生成并同步副本"，Then 三处副本域名清单与注册表逐项一致且生成 diff 无异常变更。
- **AC-2（正常路径）**：Given 技能维护者修订 Rubric 项编号（按 X5 脚本口径 15 项），When 生成副本，Then rubric.md 按脚本口径重排且不删除"时间戳准确 / 信源可靠性 / 分类正确"3 项（降级为生成期强制规则单列）。
- **AC-3（异常路径）**：Given 注册表存在语法错误或重复域名，When 技能维护者触发生成，Then 系统拒绝生成并给出具体错误行号与修复建议，不产出半成品副本。
- **AC-4（异常路径）**：Given 生成过程中某副本文件被外部占用不可写，When 触发生成，Then 系统报错并保持原副本不变，不产生部分更新。

#### 5.1.7 外部集成接口

- 依赖现有 references 目录文件作为生成目标，无外部系统调用；生成结果作为 F2 CI 校验的输入。

### 5.2 US-2：技能维护者触发三副本一致性校验与提交阻断（F2）

#### 5.2.1 业务场景

- **视角**：技能维护者
- **描述逻辑**：每次规则变更提交时，技能维护者需要确认根目录与 TRAE 镜像逐文件一致、脚本域名清单与 sources.md 双向差集为 0，避免"文件间引用失效导致加载到过时规则"（D1 反例黑名单 #12）。

#### 5.2.2 业务流程

- **Given** 技能维护者提交规则变更到仓库（或手动触发校验）；
- **When** CI 流水线执行三副本一致性校验；
- **Then** diff 与双向差集均为 0 时放行提交；差异非 0 时阻断提交，并在规则一致性页给出差异明细与修复指引。

#### 5.2.3 UE 原型

运行看板 · 规则一致性页：

```
规则一致性校验
├─ 根目录 vs TRAE 镜像 逐文件 diff：IDENTICAL / DIFFERENT
├─ 脚本 A_LEVEL_DOMAINS vs sources.md A 级清单 双向差集：0 / N 项
├─ 结果：✓ 一致 或 ✗ 阻断（附差异明细）
└─ 操作：手动触发校验 / 跳转修复指引
```

#### 5.2.4 业务逻辑

1. 校验范围：根目录与 `.trae` 镜像逐文件 diff（8 文件），以及脚本域名清单与 sources.md 双向差集；
2. 差异判定：任一 diff 非 0 即校验失败，阻断提交与发布；
3. 校验结果事件写入运行状态与指标库，供规则一致性页展示；
4. 修复指引：按差异类型给出"以注册表重新生成"或"手动同步"两类建议。

#### 5.2.5 数据描述

| 数据项 | 来源 | 流向 | 说明 |
| --- | --- | --- | --- |
| diff 结果 | CI 校验 | 校验报告 | 逐文件字节级比对结果 |
| 双向差集 | 脚本清单 vs sources.md | 校验报告 | sources 有而脚本无 5 个学术域名、脚本有而 sources 无 12 个媒体域名需归零 |
| 校验事件 | 校验动作 | 运行状态与指标库 | 供看板展示 |

#### 5.2.6 验收标准 AC

- **AC-1（正常路径）**：Given 三副本已由 US-1 单向生成且无手工改动，When CI 执行一致性校验，Then diff = 0 且双向差集 = 0，提交被放行。
- **AC-2（异常路径）**：Given 某副本被手工改动导致差异，When CI 执行一致性校验，Then 校验失败并阻断提交，规则一致性页展示差异明细（含 X1 类域名差、X7 类双向差集）。
- **AC-3（异常路径）**：Given 校验发现脚本域名清单与 sources.md 双向差集不为 0，When 技能维护者尝试发布任何日报，Then 发布动作被拦截，直至差集归零。
- **AC-4（正常路径）**：Given 规则一致性页存在"手动触发校验"入口，When 技能维护者点击触发，Then 系统立即重新执行校验并刷新结果。

#### 5.2.7 外部集成接口

- 依赖 CI 流水线（提交钩子）与运行状态与指标库（校验事件落库）；无外部服务调用。

### 5.3 US-3：技能维护者确认 X1–X16 裁决固化与回归用例守护（F3）

#### 5.3.1 业务场景

- **视角**：技能维护者
- **描述逻辑**：上游 16 组规则冲突（X1–X16）已由业务架构师逐组裁决，技能维护者需要确保裁决写入规则文件且每组有回归用例，防止后续修订把裁决悄悄回退（如 X9 HBM 归属、X11 股价边界、X16 元信息格式）。

#### 5.3.2 业务流程

- **Given** 技能维护者完成规则修订并触发生成；
- **When** 系统在生成后自动运行回归用例集；
- **Then** 16 组裁决对应的回归用例全部通过时放行；任一条失败时阻断并指出被回退的裁决条款。

#### 5.3.3 UE 原型

规则治理中心 · 回归用例守护：

```
回归用例集（16 组裁决，每组 ≥ 1 条）
├─ X9 HBM 量产归属制造：用例 RUNNING / PASS
├─ X11 股价仅作一句佐证：用例 RUNNING / PASS
├─ X16 blockquote 三行半角冒号：用例 RUNNING / PASS
└─ 结果：16/16 PASS 或 ✗ 阻断（附失败用例与裁决条款）
```

#### 5.3.4 业务逻辑

1. 回归用例库与裁决条款一一绑定，每条用例校验一个裁决的唯一结论；
2. 生成或修订触发回归执行，结果决定提交放行；
3. 失败用例定位到具体裁决编号与规则文件行，供技能维护者定点修复；
4. 完整版 F15 分类争议回收的月度增补条款同步追加回归用例。

#### 5.3.5 数据描述

| 数据项 | 来源 | 流向 | 说明 |
| --- | --- | --- | --- |
| 裁决条款 | 高层架构 §3.4 X1–X16 | 规则文件 | 落地为规则条款 |
| 回归用例 | 裁决条款生成 | 回归用例库 | 每组至少 1 条 |
| 回归结果 | 用例执行 | 校验报告 | PASS/FAIL |

#### 5.3.6 验收标准 AC

- **AC-1（正常路径）**：Given 16 组裁决全部写入规则文件且各组回归用例配置齐备，When 触发回归执行，Then 16/16 用例通过，提交放行。
- **AC-2（异常路径）**：Given 某次修订把 X9 的 HBM 归属改回"封测"，When 触发回归执行，Then 对应用例失败并阻断提交，提示"X9 裁决被回退：HBM 量产应归制造"。
- **AC-3（异常路径）**：Given 某裁决条款尚未固化（如仅改文档未改规则文件），When 触发回归执行，Then 用例失败并列出未落地裁决清单。

#### 5.3.7 外部集成接口

- 依赖规则文件与回归用例库，无外部系统调用。

### 5.4 US-4：运维值守确认工作日定时自动触发生成（F4）

#### 5.4.1 业务场景

- **视角**：运维值守（调度触发中心）
- **描述逻辑**：每工作日 08:30，系统以非交互模式自动启动一次日报生成，自动装载最近一个工作日的日期范围与默认关注领域，无需任何人触发。这是把"人工在场约 10 分钟/期"降到"仅终审 ≤ 2 分钟/期"的前提（对齐 V2）。

#### 5.4.2 业务流程

- **Given** 到达工作日 08:30 且无人工补跑冲突；
- **When** 调度触发中心按 Prefect 定时规则拉起非交互生成任务；
- **Then** 自动装载默认日期范围（最近一个工作日）与默认关注领域，进入 6 步流程；节假日（0 条新闻）按既有兜底逻辑自动 PASS。

#### 5.4.3 UE 原型

运行看板 · 运行总览页（调度相关）：

```
运行总览
├─ 今日任务：2026-08-07 08:30 触发，状态 SUCCESS / FAILED / RUNNING
```

### 5.5 US-5：生成编排引擎执行 6 步流程与门禁回退（F5）

#### 5.5.1 业务场景

- **视角**：生成编排引擎（系统行为）
- **描述逻辑**：一次生成任务按 6 步执行：范围确认 → 检索与来源分级 → 分类摘要与技术注解 → 组装 → Rubric 自检与脚本硬校验 → 保存。任一门禁 FAIL 项按 Rubric-Step 映射表回退对应步骤重跑，循环上限 5 次，超限保留最后一次结果并标注 FAIL 项。

#### 5.5.2 业务流程

- **Given** 生成任务已启动且默认参数装载完成；
- **When** 编排引擎顺序执行 Step 1 → Step 2 → Step 3 → Step 4 → Step 5，并在 Step 5 调用硬校验器；
- **Then** 校验全 PASS 则进入草稿态待终审；存在 FAIL 则按映射表回退对应 Step 重跑，循环计数 +1，超过 5 次则保留最后一次结果并标注 FAIL 项。

#### 5.5.3 UE 原型

运行看板 · 运行总览页（单期详情）：

```
单期运行详情
├─ 流程：Step1 范围确认 → Step2 检索分级 → Step3 分类摘要 → Step4 组装 → Step5 自检校验
├─ 回退记录：#4 摘要规范 → 回退 Step3（第 1 次）→ 重新生成摘要
├─ 循环计数：2 / 5
└─ 终态：门禁未过（保留结果并标注 FAIL 项）
```

#### 5.5.4 业务逻辑

1. 6 步节点划分、Rubric-Step 回退映射、门禁网关位置在 MVP 顺序编排与完整版状态机中保持不变（演进纪律）；
2. Rubric-Step 映射表：如 #1→Step4、#2→Step2、#4 摘要规范→Step3、#11→Step3、#13→Step2 等；
3. 回退循环上限 5 次（D8 max_retry），超限保留最后结果并标注 FAIL 项及原因；
4. 自动重试不得跳过门禁网关（Prefect 重试与编排回退均须重新过校验）。

#### 5.5.5 数据描述

| 数据项 | 来源 | 流向 | 说明 |
| --- | --- | --- | --- |
| 6 步执行状态 | 编排引擎 | 运行状态与指标库 | 每步状态事件 |
| FAIL 项 | 硬校验器 | 编排引擎 | 触发回退 |
| 回退映射 | Rubric-Step 映射表 | 编排引擎 | 决定回退目标 |
| 循环计数 | 编排引擎 | 运行状态与指标库 | 上限 5 |

#### 5.5.6 验收标准 AC

- **AC-1（正常路径）**：Given 6 步流程首次执行且门禁全部 PASS，When 编排引擎完成 Step 5，Then 产物进入草稿态待终审，循环计数为 0，运行事件记录 SUCCESS。
- **AC-2（正常路径）**：Given 摘要规范项（#4）FAIL，When 编排引擎执行回退，Then 回退到 Step 3 重新压缩摘要后重新组装并再次校验，循环计数 +1。
- **AC-3（异常路径）**：Given 同一 FAIL 项经 5 次回退仍不过，When 编排引擎达到循环上限，Then 保留最后一次结果并标注 FAIL 项及原因，产物停留草稿态，不自动发布。
- **AC-4（异常路径）**：Given 某步异常中断（如 LLM 超时），When 编排引擎捕获异常，Then 产生失败事件并进入可重跑状态（MVP 整期重跑，完整版走 US-11 断点恢复）。

#### 5.5.7 外部集成接口

- 依赖外部检索（Step 2）、LLM 推理（Step 3）、硬校验器（Step 5）；编排层自身不感知定时与告警（职责边界见高层架构 §5.2）。

- **When** 系统调用硬校验器执行 15 项自动校验；

### 5.7 US-7：检索与来源分级执行 A 级占比即时保障（F7）

#### 5.7.1 业务场景

- **视角**：检索与来源分级（系统行为）
- **描述逻辑**：Step 2 按 v5.0 三层搜索策略执行：第一层 A 级 `site:` 限定搜索（确保 A 级 ≥ 30%）、第二层按 5 环节产业新闻搜索（每环节至少 1 中 + 1 英）、第三层技术突破搜索（ISSCC 2026 / VLSI Symposium 2026 / DAC 2026 / IEDM 2026 / chip breakthrough）。按 URL 域名即时判级，占比不足 30% 立即补搜。

#### 5.7.2 业务流程

- **Given** Step 2 开始执行三层检索；
- **When** 系统按 A 级站内限定、5 环节双语、技术突破三层策略检索并对每条 URL 域名即时判级、即时去重、即时时效标注；
- **Then** A 级占比 ≥ 30% 时进入下一步；不足 30% 时立即补搜直至达标或耗尽检索轮次上限（3 次）。

#### 5.7.3 UE 原型

运行看板 · 运行总览页（Step 2 详情）：

```

├─ 第二层 5 环节双语：每环节 ≥ 1 中 + 1 英
├─ 第三层 技术突破：ISSCC / VLSI / DAC / IEDM / chip breakthrough
├─ A 级占比：16 / 22 = 72.7% ≥ 30% ✓
└─ 补搜记录：占比不足触发补搜 0 次
```

#### 5.7.4 业务逻辑

1. 来源级别基于 URL 域名判定，不依赖 display text（防注入，D1 设计哲学⑤ / 反例 #13）；
2. 即时去重：同事件多来源合并并标多链接；即时时效标注：> 3 天标 `[回顾]`；
3. 占比判定：A 级占比 = A 级条数 /（A 级 + B 级条数），C 级发现即丢弃；
4. A 级不足 30% 立即补搜，检索轮次上限 3 次；无结果时切备用引擎重试 1 次；单页抓取超时 15 秒，失败标"链接待验证"并保留标题摘要。

| 数据项 | 来源 | 流向 | 说明 |
| --- | --- | --- | --- |
| 候选新闻 | 三层检索 | 分级结果 | 每条含 URL 域名 |
| 来源级别 | 域名判级 | A/B/C 分级 | 只看域名不看 display text |
| A 级占比 | 分级统计 | Step 3 输入 | ≥ 30% 保障 |
| 补搜记录 | 补搜动作 | 运行状态与指标库 | 供看板展示 |

- **AC-2（异常路径）**：Given 首轮检索 A 级占比不足 30%，When 系统判定占比不足，Then 立即按 A 级站内限定补搜，补搜后达标则继续、耗尽 3 次轮次仍不足则标注"今日权威源不足"并记录指标。
- **AC-3（异常路径）**：Given 检索结果出现 C 级社媒域名（微博 / Twitter / 抖音等），When 系统判级，Then 该条目即时丢弃，不进入候选集。

1. 看板只读运行状态与指标库中的运行元数据，不呈现未发布正文；

4. 规则变更事件（规则一致性校验结果）亦推送至看板。

#### 5.9.5 数据描述

| 数据项 | 来源 | 流向 | 说明 |
| --- | --- | --- | --- |
| 运行事件 | 生成编排引擎 | 运行状态与指标库 | 状态、耗时、回退次数 |
| 门禁结果事件 | 质量门禁与自检 | 运行状态与指标库 | FAIL/WARN 明细 |
| 指标聚合 | 运行状态与指标库 | 运行看板 | 保留 90 天 |

#### 5.9.6 验收标准 AC

- **AC-1（正常路径）**：Given 运行看板已积累近 30 期数据，When 运维值守打开运行总览页，Then 展示成功率、门禁一次通过率、A 级占比、条数分布与 FAIL 排行。
- **AC-2（异常路径）**：Given 某期存在 FAIL 项，When 技能维护者在 FAIL 归因页下钻，Then 可按检查项定位到具体期次与条目，并查看修正建议。
- **AC-3（异常路径）**：Given 看板请求超过 90 天前的指标，When 查询执行，Then 系统提示数据已过保留窗口不展示（指标保留 90 天）。
- **AC-4（正常路径）**：Given 看板数据更新，When 页面刷新，Then 只读运行元数据，未发布日报正文不出现于任何看板页面。

#### 5.9.7 外部集成接口

- 依赖运行状态与指标库（本地留存）与规则治理中心（规则变更事件）；无外部服务调用。

### 5.11 US-11：运维值守使用状态化编排与断点恢复（F10，完整版）

#### 5.11.1 业务场景

- **视角**：运维值守
- **描述逻辑**：完整版将 6 步流程由顺序编排替换为状态机承载（LangGraph StateGraph + Checkpointer），每步持久化。任务中途异常时可从断点续跑而非整期重来，降低失败恢复成本。

#### 5.11.2 业务流程

- **Given** 完整版运行中，一次生成任务在 Step 3 中断；
- **When** 运维值守从断点恢复该任务；
- **Then** 系统从 Step 3 检查点继续执行，不重复 Step 1/Step 2 已完成的检索与分级结果。

#### 5.11.3 UE 原型

运行看板 · 运行总览页（断点恢复）：

```
断点恢复
├─ 中断位置：Step 3 分类摘要（LLM 超时）
├─ 检查点：Step 1/Step 2 结果已持久化
├─ 操作：从断点续跑（复用已完成结果） / 整期重跑
└─ 恢复后：继续 Step 3 → Step 4 → Step 5
```

#### 5.11.4 业务逻辑

1. MVP 顺序编排在完整版被状态机替换时，6 步节点划分、Rubric-Step 回退映射、门禁网关位置三者保持不变，只替换执行引擎；
2. 每步状态持久化（Checkpointer），异常后可从断点续跑；
3. 断点恢复不跳过门禁网关，恢复后 Step 5 仍必须完整校验。

#### 5.11.5 数据描述

| 数据项 | 来源 | 流向 | 说明 |
| --- | --- | --- | --- |
| 步状态快照 | 编排引擎 | 持久化检查点 | 每步完成后写入 |
| 断点位置 | 中断事件 | 编排引擎 | 恢复起点 |
| 恢复记录 | 恢复动作 | 运行状态与指标库 | 供看板展示 |

#### 5.11.6 验收标准 AC

- **AC-1（正常路径）**：Given 任务在 Step 3 中断且检查点已持久化，When 运维值守选择断点续跑，Then 从 Step 3 继续执行，不重复已完成步骤。
- **AC-2（异常路径）**：Given 中断发生在门禁校验前且产物已组装，When 恢复执行，Then 恢复后 Step 5 仍执行完整校验，退出码 1 仍拦截发布。
- **AC-3（异常路径）**：Given 检查点数据损坏无法恢复，When 运维值守尝试断点续跑，Then 系统回退为整期重跑并告警提示检查点异常。

#### 5.11.7 外部集成接口

- 依赖 LangGraph Checkpointer（本地持久化）与运行状态与指标库；MVP 阶段该能力由"门禁网关后空实现钩子"占位（演进纪律）。

### 5.12 US-12：技能维护者接入语义质量校验层（F11，完整版）

#### 5.12.1 业务场景

- **视角**：技能维护者（面向日报终审人与读者的产物质量提升）
- **描述逻辑**：完整版接入 DeepEval 式语义校验层，对摘要忠实度、技术注解正确性、分类正确性做自动评估。以"确定性规则 + LLM 评委"双层评估补强纯规则脚本的语义盲区；先记录不拦截灰度 4 周后转为 WARN 输出，硬门禁始终由规则脚本兜底（U-02 裁决落地）。

#### 5.12.2 业务流程

- **Given** 完整版已接入语义校验层钩子；
- **When** 每期产物通过硬门禁后，语义校验层对摘要忠实度、技术注解正确性、分类正确性抽检评估；
- **Then** 灰度期（前 4 周）只记录不拦截，之后转为 WARN 输出并生成抽检报告，硬门禁仍由 `validate_report.py` 兜底。

#### 5.12.3 UE 原型

运行看板 · 质量趋势页（语义校验）：

```
语义质量抽检报告
├─ 摘要忠实度抽检合格率：92%（目标 ≥ 90%）
├─ 技术注解正确率：94%（目标 ≥ 90%）
├─ 分类正确率：91%（目标 ≥ 90%）
├─ 灰度状态：记录不拦截（第 3 周） / WARN 输出
└─ 操作：下钻不合格样本 / 双周校准评委
```

#### 5.12.4 业务逻辑

1. 语义校验层以确定性规则 + LLM 评委双层评估，评委偏差需人工校准；
2. 灰度 4 周"先记录不拦截"，后转 WARN 输出；不取代 `validate_report.py` 的硬门禁地位；
3. 承接 rubric 独有的"时间戳准确 / 信源可靠性 / 分类正确"3 项生成期强制规则的自动判定（X5 裁决）；
4. 抽检不合格样本回流提示词与技术注解规则（语义质量回路，双周校准）。

#### 5.12.5 数据描述

| 数据项 | 来源 | 流向 | 说明 |
| --- | --- | --- | --- |
| 抽检样本 | 当期产物 | 语义校验层 | 摘要 / 注解 / 分类 |
| 合格率 | 校验层评估 | 抽检报告 | 三指标 ≥ 90% |
| 不合格样本 | 校验层 | 提示词修订 | 双周校准 |

#### 5.12.6 验收标准 AC

- **AC-1（正常路径）**：Given 完整版上线且语义校验层接入，When 每期产物通过硬门禁，Then 语义校验层执行抽检并输出三指标合格率。
- **AC-2（异常路径）**：Given 灰度期内抽检发现技术注解错误（如氧化镓配碳化硅注解），When 校验层评估，Then 只记录不拦截，产物照常发布并计入抽检报告。
- **AC-3（异常路径）**：Given 灰度期后某期分类正确率低于 90%，When 校验层转为 WARN 输出，Then 产物可发布但 WARN 计入质量指标，提示词与技术注解规则进入修订队列。
- **AC-4（正常路径）**：Given 语义校验层与硬门禁同时存在，When 同一产物先经硬门禁再经语义层，Then 硬门禁退出码仍为最终发布裁决依据，语义层不改变发布拦截判定。

#### 5.12.7 外部集成接口

- 依赖 LLM 推理服务（LLM 评委）与既有 15 项 Rubric 规则；DeepEval 式评估能力按开源组件自托管方式接入。

- **When** 合规审阅抽查不少于 10 期日报的来源级别、免责声明与中立性；
- **Then** 抽查结果全部合规时归档留痕；发现问题时标记不合规项并触发规则治理回路修订。

#### 5.15.3 UE 原型

合规抽查视图（复用日报产物 + 运行看板只读数据）：

```
月度合规抽查
├─ 抽查期数：10 期（近 90 天窗口内）
├─ 来源级别：C 级 0 条 / 无链接条目 0 条
├─ 免责声明：10/10 期含免责声明与 --- 分隔线
├─ 中立性：10/10 期无投资建议关键词命中
└─ 结果：✓ 合规 或 ✗ 不合规（附期次与条目定位）
```

#### 5.15.4 业务逻辑

1. 合规抽查数据来源为已发布归档产物与运行状态与指标库（只读）；
2. 抽查维度：来源级别（C 级 0 条、可追溯率 100%）、免责声明完整性、中立性（无投资建议措辞）；
3. 不合规项标记后进入规则治理回路（周度规则修订 / 月度仲裁增补）；
4. 指标保留 90 天满足每月抽查回溯需求。

#### 5.15.5 数据描述

| 数据项 | 来源 | 流向 | 说明 |
| --- | --- | --- | --- |
| 抽查期次 | 产物归档库 | 抽查清单 | 近 90 天窗口 |
| 来源级别统计 | 自检结果小节 | 抽查结果 | A/B/C 分级 |
| 不合规项 | 抽查动作 | 规则治理回路 | 触发修订 |

#### 5.15.6 验收标准 AC

- **AC-1（正常路径）**：Given 抽查 10 期日报，When 合规审阅核对来源级别，Then C 级来源 0 条、无链接条目 0 条，抽查合规。
- **AC-2（异常路径）**：Given 某期日报含投资建议关键词措辞但未被硬门禁拦截（如措辞绕过关键词表），When 合规审阅抽查发现，Then 标记不合规项并提交规则治理回路，进入周度修订队列。
- **AC-3（正常路径）**：Given 合规审阅需回溯 3 个月前数据，When 查询近 90 天窗口，Then 指标与产物可完整回溯（指标保留 90 天）。

#### 5.15.7 外部集成接口

- 依赖产物归档库与运行状态与指标库（只读）；无外部服务调用。

## 6. 非功能性需求

> 本章回收 US 旅程中隐含的非功能性约束，与《高层架构设计》§6.1 N1–N4 硬指标对齐；§6.1~§6.4 全部子节均有内容。

### 6.1 易用性需求

- **操作便利性**：终审发布台核心路径（打开草稿 → 复核自检表 → 逐条抽查 → 确认发布）≤ 4 步；运行看板支持按状态筛选、一键重跑、单期日志查看。
- **UI 一致性**：终审发布台与运行看板共用同一套指标口径与命名（15 项门禁编号、A/B/C 分级、6 步流程），与日报产物中的自检表、来源分级统计口径一致，避免"两套口径并存"（对齐 X5/X6 裁决）。
- **引导提示**：门禁详情页对每条 FAIL 项给出修正建议与 Rubric-Step 映射指引；规则治理中心对注册表语法错误给出具体行号与修复建议。
- **错误反馈**：任一校验失败、生成失败、抓取失败均给出可读的错误信息与下一步操作建议，杜绝"只有退出码 0/1"。
- **无障碍支持**：本地 Web 复核页与看板遵循基础可读性要求（字号、对比度、键盘可操作），面向内部单机单用户场景，不引入额外无障碍标准。

### 6.2 性能响应需求

| 指标 | 目标值 | 来源 |
| --- | --- | --- |
| 终审首屏加载（正文 + 15 行自检表） | P95 ≤ 2 秒 | 高层架构 §6.4 |
| 单期端到端耗时（含最多 5 次门禁回退） | ≤ 30 分钟 | 高层架构 §6.1 N1 |
| 告警时延（事件产生到触达值守） | ≤ 5 分钟 | 高层架构 §6.1 N4 / §6.5 |
| 定时任务成功率 | ≥ 95%（MVP 退出标准） | 高层架构 §4.3 |
| 门禁一次通过率 | ≥ 90%（MVP 上线后 1 个月） | 高层架构 §1.3 |
| 人工在场时长 | ≤ 2 分钟 / 期（仅终审确认） | 高层架构 §1.3 |
| 指标保留窗口 | 90 天 | 高层架构 §6.5 |
| 并发与吞吐 | 单实例单编辑部运行，无多租户并发诉求；定时任务与人工补跑互斥串行，同刻仅 1 个生成任务 | 高层架构 §4.2 |
| 数据规模上限 | 近 30 期看板展示、近 90 天指标留存、近 14 期事件指纹窗口（完整版） | 高层架构 §6.3 F12 |

### 6.3 操作与环境需求

- **浏览器 / 客户端兼容性**：本地 Web 看板（Prefect UI 或自建 Web 看板）需在主流现代浏览器（Chrome / Edge 最新两个大版本）可用；MVP 终审台以命令行文本终审加本地静态复核页为最小形态。
- **网络环境**：仅出域调用公开新闻检索与 OpenAI 兼容 LLM API；正文、规则、运行元数据全部本地留存，数据不出域（N2）；公网不稳定时，检索无结果切备用引擎重试 1 次，单页抓取超时 15 秒。
- **设备规格**：单节点自托管服务化部署（经中间确认 U-01 方案B），单机单用户定位，不引入租户模型；`validate_report.py` 保持 Python 3 标准库实现、零第三方依赖，可脱离系统独立运行（N3）。
- **运行环境约束**：LangGraph（MIT）、Prefect Server（Apache 2.0）全开源自托管，不引入任何订阅型外部组件。

### 6.4 安全性需求

> 满足相关安全标准；本项目为单节点自托管、数据不出域系统，安全设计侧重防注入判级、防发布绕过、接口调用安全与数据本地留存。

#### 6.4.1 安全密码设置

- 终审发布台与运行看板如启用账号口令访问，密码需达到 8 位以上大小写字母 + 数字 + 特殊字符的强度要求；
- 值班通知渠道、看板登录等凭据禁止明文落库，统一走密钥管理（由安全设计承接）。

#### 6.4.2 安全软件架构

- 应保证自身结构中各模块的通信安全：本地服务间通信仅绑定本机回环地址，不对外暴露非必要端口；
- 应保证组件、用户、资源的认证与访问控制：终审发布台为唯一发布出口，门禁未过无绕过路径；运行看板只读运行元数据，不呈现未发布正文，避免形成第二个发布出口；
- 与外部系统交互安全：仅出域调用公开检索与 LLM API，使用 HTTPS 安全通讯协议；仅传递检索所得公开正文与生成请求，不外传规则文件与运行元数据；对 LLM API 密钥使用安全存储与最小权限配置。

#### 6.4.3 安全设计

- 应提供认证授权功能：单机单用户场景下，发布动作（终审确认）与配置动作（规则修订、告警配置）按角色最小授权；终端用户的发布权限由终审台强制校验门禁结果保证，不引入额外权限模型。

#### 6.4.4 安全开发

- 应对函数入口参数的合法性和准确性进行检查：校验器 CLI 对日报文件路径、编码（utf-8 → gbk → utf-16 fallback）做存在性与合法性检查；
- 应进行输入边界检查：摘要句数、字数、URL 格式、域名格式均有长度与格式限制；
- 应保证不因代码的编写导致出现可被直接利用的高危漏洞：来源判级只取 URL 域名且忽略 display text（防注入，D1 反例 #13），C 级域名精确匹配防子串误匹配（如 x.com 不误匹配 fox.com）；
- 应在输入输出模块中进行适当过滤：输出产物按模板锁定结构与章节顺序，防止越界附录与越界内容；
- 禁止使用未经授权和验证的代码：仅复用既有 `validate_report.py`（v5.0）与开源组件（LangGraph / Prefect），不引入未经评估的第三方依赖；
- 应保证应用程序不存在任何可绕行安全机制的行为或遗留后门：发布按钮强制禁用逻辑与命令行无绕过参数需经测试验证。

#### 6.4.5 安全测试和部署

- 应进行安全扫描测试：上线前对 Web 看板与终审台做基础安全扫描；
- 应进行安全配置基线检查：单节点 Docker 基线配置（端口、密钥、日志）按安全基线核对；
- 应进行安全功能的测试：发布拦截（退出码 1 强制禁用）、防注入判级（display text 伪装 A 级域名）、C 级域名精确匹配均有测试用例；
- 系统在上线前应不存在高危风险：三副本一致性、回归用例守护、发布拦截作为门禁测试项纳入上线检查。

#### 6.4.6 数据安全

- **数据存储和传输加密**：正文、规则、运行元数据全部本地留存，数据不出域（N2）；LLM API 调用通过 HTTPS 传输，仅传递公开正文与生成请求；用户口令、API 密钥等重要数据的存储与传输按安全设计采用加密与安全存储方案；历史产物（D9/D10/D11）作为格式基线不追溯修订，仅作只读参考。
